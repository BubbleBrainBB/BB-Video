# Promo workflow (paced by the beat)

> Part of **bb-video**: read `../SKILL.md` first (styles, which workflow to use). This file is the workflow for promos with no narration and beat-synced music: websites, apps, software products.

You write the frames yourself in HTML + CSS, Chrome renders them frame by frame, code composes the music and sound effects, and ffmpeg outputs the mp4.
Each frame is drawn by the pure function `renderFrame(t)`, and the rhythm sits on the music's beat. **Animation libraries are allowed** (GSAP and its plugins, Three.js, Matter.js, opentype.js, etc.), but time is always driven by our clock (see the "Animation libraries" section of `references/motion.md`).

Relative paths in this file are relative to this folder (`bb-video/promo/`).

## Contents
- `references/structure.md`: the film's structure, beats and section lengths. **Read before writing the storyboard.**
- `references/motion.md`: every component of the runtime `promo.js` (text, UI, camera, transitions, montage, ending). **Read before writing frame code.**
- `references/music.md`: music — improvise a piece for the product that follows the picture's rhythm (score.js). **Read before writing frames.**
- `references/sound.md`: sound design — design a set of characterful sound effects for the product (sound.js), in the same key as the music. **Read before writing frames.**
- `references/review.md`: self-review checklist.
- `../styles/<style>/STYLE.md`: the visual style (see "Visual styles" below). Once a style is chosen, **read it first**, then write the storyboard.
- `references/kit.md`: the styles' shared interface and the quick version (one script; change `style` and it becomes a film in another style). Read before offering the user several styles to pick from, or before adding a new style.
- `scripts/new.mjs` new project · `scripts/capture.mjs` research and screenshots · `scripts/render.mjs` check and render · `scripts/music.mjs` music and sound effects (called by render automatically)

## Visual styles
**Style is the only thing the user picks**: it only decides "how it looks, moves and sounds", has nothing to do with the product's content, and any product can use any style. How the film tells it (UI demo first, big type first, back-and-forth, numbers first) is decided by me from the product and the material (start of `references/structure.md`); the user doesn't pick it. Every style is written to the same outline (`../styles/TEMPLATE.md`) and implements the same set of shared moves (`references/kit.md`).

## Workflow

### 1. New project, research
```bash
node scripts/new.mjs videos/<short-english-name>                    # add --style origami / pop / op / cutout / ascii / shadow / bauhaus / pixel / chat / toy3d / newsreel / filmroom / mystery / isometric / trailer / dossier / manga / map / swiss / lumen / blueprint / collage / grain / storybook for that visual style (add --quick too for the quick version)
node scripts/capture.mjs videos/<name> --research <url>            # desktop
node scripts/capture.mjs videos/<name> --research <url> --mobile   # mobile
```
Research notes go in `research/`: title, description, headings at every level, button text, numbers, fonts actually loaded, main colours, all the page's text.
Then go through the key pages in the browser (open details, switch options) to confirm how features work and what the numbers mean. **Don't log in anywhere that requires it.**

**Products without a website (GitHub projects, desktop apps, command-line tools)**:
1. Read the repo first: README, docs, changelog, screenshots and icons in the repo (brand name, slogan, feature list and colours come from here).
2. README screenshots are often out of date: the real UI text comes from the **source code** (button text in components, menu items, hints, i18n files); use the original icon and logo files from the repo.
3. To see the real UI, prefer screenshots in the repo / screenshots from the user; if the user has the app installed and agrees to let you look, follow hard rule 8: look, don't touch.
4. If the end-card URL contains a personal username (github.com/someone/…), first ask the user whether it may go on screen.

### 2. Write the fact sheet `brief.md` (the most important step)
- **Facts**: what the product is, features, the exact text of buttons and options, numbers, names… each noting which page it was seen on. Live data gets an "as of" date, shown on screen too (e.g. "As of Oct 2, 2026").
- **Copy**: creative slogans, verbs (e.g. "WRITE." "Ask the people."). No invented numbers, features or reviews.
- **Off limits**: categories with no content, metrics the page doesn't explain, claims that need a login to verify.
- Fonts: when the brand uses a commercial font, substitute a free font with a similar feel, and note it in the fact sheet.
- **Colours**: take them from the product (the main and background colours in the website's CSS, buttons, logo) — research has already listed candidates in `research/colors.json` (check them against the screenshots); write one line `颜色：#… （来自：…）` or in English `Colours: #… (from: …)`; in the quick version write `film({ brand })`; each style applies them with its own materials (`references/kit.md`). When a style has several grounds (launch: light / dark / brand colour), choose by the product's own UI — light products get a light ground, dark products a dark ground, a signature brand colour gets the brand-colour ground; don't default to dark.
- **Sound = music + sound effects**: music carries rhythm and mood (`score.js`, `references/music.md`), sound effects carry detail and texture (`sound.js`, `references/sound.md`). First write one sentence on what this product sounds like, find 1–2 real materials from the product, put both in the same key, and write it under "Sound" in the fact sheet.

**Every piece of text on screen must be findable in brief.md** (`render.mjs --check` checks them one by one). When demoing "action → result", the result must truly correspond (e.g. for an image-generation demo, use that image's real prompt and model).

### 3. Capture assets
List the screenshots to take in `shots.json` (format at the top of `scripts/capture.mjs`), then:
```bash
node scripts/capture.mjs videos/<name>                 # all
node scripts/capture.mjs videos/<name> --only logo,hero  # only some
```
Common ones: desktop first screen, full-page long shot (`fullpage`), mobile first screen and long shot (for portrait), logo (`clip`, 4× sharpness), key cards / charts (element screenshots), a clean homepage hero (`clean`).
Afterwards look through them with Read: blank captures, wrong elements, anything covered by the nav bar.

**Archive photos** (a launch told as news, history, the product's real hardware — when the user has none): `node scripts/footage.mjs videos/<name> search "<query>"` lists licence-clean files from Wikimedia Commons (CC0 / public domain / CC BY by default); tell the user what you want to fetch (title, source, licence, size), wait for their OK, then `fetch <n>` → `assets/src/` with a credit sidecar (videos: `--from <s> --dur <s>` fetches only that stretch), and run `node ../explainer/scripts/assets.mjs videos/<name>`. Credits end up in `out/CREDITS.txt`.

**When you can't capture it, or it isn't sharp** (sharpness from high to low, try in order; no step ever bypasses bot checks or logs into someone else's account):
1. `capture.mjs` (headless Chrome, 2–4× sharpness) — sites with Cloudflare-style bot checks will block it: don't get around it, move to the next option.
2. The built-in browser: screenshots are scaled to the panel size (e.g. a 1284-wide page → an 800-wide screenshot). First set the viewport no wider than the panel with `resize_window` (e.g. 820×900) so the capture is 1:1 (still only 1× sharpness); capture the main column and avoid people's names in sidebars. Products the user is already logged into can only be captured this way (look, don't touch, hard rule 8).
3. An app installed on the user's computer (with the user's consent, computer-use look-only): about 1–1.3× sharpness, good for one card or one panel; crop out or avoid personal information such as names, emails and conversation titles. `screencapture` in Bash usually lacks screen-recording permission.
4. When none is sharp enough: use real screenshots only for small areas paired with big-type captions (still legible at 1.5–2×); redraw the rest of the UI in code from the page's / app's **real text** (written into brief.md), never invented.

### 4. Storyboard
**First write the information list** (at the very top of the storyboard): the 3–5 things the viewer should remember (concrete features, real numbers, a key action or result on the real UI), each with its **evidence** (the page's text, a number, which part of a screenshot) and **the picture that carries it** — an annotated real UI, a flow, a comparison, a chart. A 30-second film must make at least 4 concrete things clear; a film of slogans and big type alone carries too little.
- The real UI is a promo's best information: plan at research time which pages and which steps to capture (`shots.json`), then box, circle or zoom the key part of a screenshot and add one line of explanation (the quick version's `annotate`; step-by-step, side-by-side and numbers also have ready-made cues, which each style draws in its own language — not boxes and arrows: see the section on info cues in `references/kit.md`). When a site blocks screenshots, ask the user for screenshots / a screen recording; don't fall back to showing only the logo.
- Each scene is one unit of information: claim + evidence + picture. The picture adds what words can't say clearly (order as a flow, better/worse as a comparison, how much as a chart).
- A frame can hold 2–4 pieces of information at once (title + an image + a few labels), building up step by step; no need to clear the frame for every line.
**Then write the rhythm sheet** (below the information list): one role per scene — opening hook (something moving within 3 s) → climb → fast cuts (at 30–60%, turn the "many things" item of the information list into a fact montage) → landing (the single most important line) → ending; at each scene change switch at least two of: energy, camera, picture type, ground colour. In the quick version this is each scene's `role` (see the rhythm-sheet section of `references/kit.md`), and `--check` prints it for checking.
Then, following `references/structure.md`, settle the length, BPM, each section's content and the effects used, and put it in a table for the user to review (skip if the user says "just make it").
**Prefer redrawing UI in code** (cards, ranking bars, buttons, forms): it can move, stays sharp, and lays out well in both landscape and portrait; use screenshots where "realness" matters (full-page scrolls, charts, photos).

### 5. Write the frames
Edit `index.html`: `PROMO.compose({ bpm, offset, duration, theme, cover, build })`; music goes in `score.js`, sound design in `sound.js`.
**No "unofficial demo / not affiliated" corner line on a promo**, whoever's product it is: nobody takes it for the company's own film, and a caption box sitting on the picture for the whole film spoils it. Don't add one unless the user asks. `bpm` is the music's tempo and also the picture's beat grid — set the music tempo before writing the frames.
- All times sit on the beat: `F.beat(n)`.
- `F.section(at, energy, { hit })` marks the music's sections; the music is arranged from these.
- Landscape and portrait are **the same code**: sizes use `F.px()`, layouts branch on `F.portrait`.
- Components emit sound events automatically (impact, transition, click, typing…); what they actually sound like is decided by `sound.js`; for your own moves use `F.sfx(t, type, volume, { dur, dir, size })`, and you can name types yourself (define them in sound.js).
- Register your own text elements with `F.text(el, 'label', text, appear, disappear)` so they take part in the fact check and the overlap check.

**Narration (optional)**: promos have no narration by default; when the user wants a voiceover, use the same tools as the explainer —
1. write `script.json` in the project (format: "script.json format" in `../explainer/GUIDE.md`; for English use an `en-US-…Neural` voice), run `python3 ../explainer/scripts/tts.py videos/<name>` to produce `audio/narration.m4a` and `timeline.js`;
2. in `index.html`, add `<script src="timeline.js"></script>` before `lib/core.js`.
After that: `F.T` is the narration timeline (`F.T.start('id')`, `F.T.word('id', 'some word')`, as in the explainer), and the beat `F.beat` still works; the film runs at least 1.5 s past the end of the narration; captions show at the bottom automatically, timed by word (`captions: false` in `compose` turns them off, `captions: { size, bg }` styles them); when rendering, the music ducks 8 dB under speech automatically, sound effects don't. The narration text itself isn't fact-checked, but facts stated in it must also be findable in brief.md.

### 6. Check (both landscape and portrait; a few seconds, no render needed)
```bash
node scripts/render.mjs videos/<name> --check                    # automatic checks: fact check, text overlap, two titles on screen at once, early reveal, dwell time, cut off by the frame edge, unreadable on a phone, silent on a phone speaker, information amount (text-only scenes, fewer than 4 concrete things in 30 s)
node scripts/render.mjs videos/<name> --check --aspect 9:16
node scripts/render.mjs videos/<name> --strip 0.5,39.5,24         # overview of the whole film
node scripts/render.mjs videos/<name> --strip 20.5,22,8           # around one transition
node scripts/render.mjs videos/<name> --strip 0.5,39.5,24 --aspect 9:16
node scripts/render.mjs videos/<name> --audio                     # only music + sound effects to preview → out/audio.wav
```
Go through `references/review.md` item by item and fix until everything passes. At the end `--check` prints the **motion sheet** (how many things move at once, duration families, linear starts/stops, flashes, too fast, sudden camera changes, and stiff motion: text switched on with no entrance, the same entrance over and over, empty boxes waiting for their words; charts in `review/motion-*.png`); how to read it is in review.md.

### 7. Render
```bash
node scripts/render.mjs videos/<name>                  # → out/video-16x9.mp4 + cover-16x9.png
node scripts/render.mjs videos/<name> --aspect 9:16    # → out/video-9x16.mp4 + cover-9x16.png
```
The final render does automatically: motion blur (6 subframes per frame, no extra time on still frames; fast moves registered with `F.blur` get more), BT.709 colour, loudness -14 LUFS, dropped / flash frame checks; the quick version also **measures the rhythm**: planned energy and measured energy are printed side by side, with a comparison chart in `review/rhythm-<ratio>.png`; too flat, no hook, and fast cuts not where planned all get flagged.
Rendering takes about 4–5× as long as without blur (45 s takes about 2.5 minutes); to just check the rhythm use `--draft` or `--blur 1`. Every final render also writes `out/captions-<ratio>.srt` when the film has captions, and `out/CREDITS.txt` when it registered picture credits (`F.credit`).

### 8. Review (the judge ≠ the maker) — on drafts, 2 rounds by default
First clear every `--check` warning (on the beat, portrait safe zone, unreadable on a phone, silent on a phone speaker… don't leave these for the reviewers to find).
Reviewers look only at **drafts** (half resolution, no motion blur, both versions in parallel in about 30 s); only once they pass do you render the final film once:
```bash
node scripts/render.mjs videos/<name> --draft & node scripts/render.mjs videos/<name> --draft --aspect 9:16 & wait
node scripts/render.mjs videos/<name> --review --draft & node scripts/render.mjs videos/<name> --review --draft --aspect 9:16 & wait
```
`--review` produces a review pack (about 10 s): `contact-*.png` overview sheets, `transitions-*.png` 1.2 s around each transition, `report-*.txt` a table of picture change / phone-band loudness / events every 0.5 s.

Then start the review with the Agent tool (prompt template at the end of `references/review.md`):
- **One reviewer for landscape and one for portrait, in parallel** (two Agents in the same message); they look only at pictures, not code, and change no files.
- **Round 1**: list every problem at once. **"Must fix" is limited to the objective problems defined in review.md** (covered, unreadable, inaudible, off the beat, visible glitches, factual errors…); taste calls like "the opening isn't gripping enough" or "this part runs long" are always "optional".
- **Round 2 (recheck)**: use SendMessage to **continue the same reviewer** (don't start a new one — every new reviewer has different standards, keeps finding new problems and never converges); it checks only its own must-fix items from the previous round + whether anything broke.
- If the recheck has no must-fix items, deliver; list the "optional" items for the user to decide whether to change more. Only do a round 3 when must-fix items remain, or the user asks for a higher bar.
- Once passed, render the final film (the commands in step 7).

## Hard rules
1. **Invent nothing**: text, numbers and features on screen all come from brief.md; live data is dated; don't explain metrics the site doesn't explain.
2. **No logging in, no submitting forms, no downloading site files**: assets are screenshots only; UI behind a login is redrawn in code.
3. **A frame is a pure function of time**: no `Date.now()`, CSS animations or transitions; for your own randomness use `EV.rng` (libraries' `Math.random` is already seeded per frame). Animation libraries may only come in through `PROMO.gsapTimeline / three / physics`; never let a library play on real time by itself, and never change state in callbacks.
4. **Everything on the beat**: transitions, impact words and clicks all land on `F.beat(n)`.
5. **Every piece of text must be readable in time**: each word of a title gets at least 0.3 s; two pieces of text must never sit on top of each other.
6. **Check both landscape and portrait**: portrait isn't landscape shrunk, it's a new layout (phone frame, vertical stacking).
7. **Aim for generality**: when an effect is missing, make it a reusable component in `promo.js` rather than hard-coding it in one project.
8. **The user's accounts and the apps on the user's machine: look, don't touch**. Website sessions the user is already logged into, and apps installed on the user's computer, may be opened, looked at and screenshotted, but **nothing is created, sent, saved, or changed in settings** (creating a task / document / conversation counts too — it leaves something in the user's data). To see the "after creating" UI, find it in the source or screenshots, or ask the user to click it themselves. If you really did leave something behind by accident, tell the user at the end what was left, where, and how to delete it. No real people's names, project names or conversation titles from the user's data appear on screen.
